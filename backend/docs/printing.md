# Module: Printing

Base path: `/api/v1/printing` (for user endpoints) and `/api/v1/admin/printing` (for admin endpoints)

All routes require authentication. Admin management routes require the `admin` role.

---

## Overview

The printing module manages manual physical 3D printing workflows with admin approval and execution steps. Unlike slicing jobs, printing jobs require explicit admin control at each stage of the lifecycle.

**Key Features:**
- Manual workflow with admin approval
- Admin-controlled state transitions
- Status tracking through PrintingJob model
- Quality control at each step
- Manual G-code download and printer operation

**Workflow:**
```
1. User calls POST /execute with slicingJobId → Job created (status: "Pending Review")
2. Admin calls POST /review → Approve (→ "Queued") or Reject (→ "Rejected")
3. Admin calls POST /start → Job starts (→ "Processing", sets startedAt)
   → Admin downloads G-code from gcodeUrl and manually sends to printer
4. Admin calls POST /complete or POST /fail → Job finishes (→ "Completed"/"Failed", sets finishedAt)
```

### `POST /api/v1/printing/execute`

- **Access:** Authenticated Users

Creates a PrintingJob from a completed slicing job with "Pending Review" status for manual workflow. The job ID is auto-generated by MongoDB.

**Request Body (JSON)**

- **`slicingJobId`** (*string*, Required)
  - *Validation:* Valid MongoDB ObjectId (24-character hex string)
  - *Description:* The ID of the completed slicing job to create a printing job from
  - *Note:* The slicing job must have status "Completed" and contain a valid gcodeUrl

**Response 200 — OK**
```json
{
  "success": true,
  "message": "PrintingJob created successfully. Awaiting review.",
  "data": {
    "jobId": "64f1a2b3c4d5e6f7a8b9c0d2",
    "jobNumber": "PRINT-1705320000000-xyz789",
    "status": "Pending Review"
  }
}
```

**Response 400 — Validation Error**
```json
{
  "success": false,
  "message": "Validation failed",
  "data": {
    "errors": [
      { "field": "slicingJobId", "message": "slicingJobId must be a valid MongoDB ObjectId" }
    ]
  }
}
```

**Response 400 — Slicing Job Not Completed**
```json
{
  "success": false,
  "message": "Slicing job must be completed before creating a printing job. Current status: Processing"
}
```

**Response 404 — Slicing Job Not Found**
```json
{
  "success": false,
  "message": "Slicing job not found"
}
```

**Response 401 — Unauthenticated**
```json
{ 
  "success": false, 
  "message": "You are not logged in. Please log in to get access." 
}
```

**Response 403 — Forbidden**
```json
{ 
  "success": false, 
  "message": "You do not have permission to perform this action." 
}
```

### `POST /api/v1/admin/printing/start`

- **Access:** Admin only

Manually starts a PrintingJob (transitions from "Queued" to "Processing").

> **Workflow:** Admin downloads the G-code file from `gcodeUrl` and manually sends it to the physical 3D printer. This endpoint marks the job as started in the system.

**Request Body (JSON)**

- **`jobId`** (*string*, Required)
  - *Validation:* Valid MongoDB ObjectId
  - *Description:* The ID of the PrintingJob to start

- **`machineId`** (*string*, Optional)
  - *Validation:* Non-empty string, trimmed
  - *Description:* The 3D printer identifier (for tracking purposes)

**Response 200 — OK**
```json
{
  "success": true,
  "message": "PrintingJob started successfully.",
  "data": {
    "jobId": "64f1a2b3c4d5e6f7a8b9c0d1",
    "jobNumber": "PRINT-2024-001",
    "status": "Processing",
    "machineId": "PRINTER-01",
    "startedAt": "2024-01-15T11:00:00Z",
    "gcodeUrl": "https://drive.google.com/file/d/abc123/view"
  }
}
```

> **Note:** The `gcodeUrl` in the response is the G-code file that should be downloaded and sent to the printer manually.

**Response 404 — Not Found**
```json
{
  "success": false,
  "message": "PrintingJob not found."
}
```

**Response 400 — Invalid Transition**
```json
{
  "success": false,
  "message": "Invalid status transition. Job must be in 'Queued' status."
}
```

## Data Model

### PrintingJob

Represents a manual printing operation requiring admin approval and execution.

**Fields:**

- **`_id`** — MongoDB ObjectId
- **`jobNumber`** — Unique string within PrintingJob collection (e.g., "PRINT-2024-001")
- **`slicingJobId`** — ObjectId ref → SlicingJob (required, must reference a completed slicing job)
- **`status`** — `"Pending Review"` | `"Approved"` | `"Rejected"` | `"Queued"` | `"Processing"` | `"Completed"` | `"Failed"` (default: `"Pending Review"`)
- **`gcodeUrl`** — String (URL to G-code file, required, obtained from slicing job)
- **`machineId`** — Optional string (3D printer identifier)
- **`fileName`** — String (G-code file name, required, obtained from slicing job)
- **`startedAt`** — Optional Date (timestamp when printing started, set manually by admin)
- **`finishedAt`** — Optional Date (timestamp when printing completed or failed, set manually by admin)
- **`operatorId`** — Optional ObjectId ref → User (user who created the job)
- **`createdAt`** — Date (auto-managed by timestamps)
- **`updatedAt`** — Date (auto-managed by timestamps)

**Status Flow:**
```
Pending Review → Approved → Queued → Processing → Completed
              → Rejected                       → Failed
```

**Constraints:**
- `jobNumber` is unique within the PrintingJob collection
- `slicingJobId` is required and must reference a valid SlicingJob document with status "Completed"
- `gcodeUrl` and `fileName` are required and obtained from the referenced slicing job
- Indexed fields: `jobNumber`, `slicingJobId`, `status`

## Workflow Details

### Manual Printing Workflow

The printing workflow requires manual admin approval and execution:

**Step 1: Job Creation**
- User calls `POST /execute` with a completed slicingJobId
- System validates the slicing job exists and has status "Completed"
- System validates the slicing job has a valid gcodeUrl
- System generates unique jobNumber (format: `PRINT-{timestamp}-{random}`)
- System creates PrintingJob document with status `"Pending Review"`
- System copies gcodeUrl and fileName from the slicing job

**Step 2: Review**
- Admin calls `POST /review` with action "approve" or "reject"
- If approved: Status → `"Approved"` → `"Queued"` (automatic)
- If rejected: Status → `"Rejected"` (terminal state, no further transitions)

**Step 3: Execution**
- Admin calls `POST /start` with jobId and optional machineId
- Status: `"Queued"` → `"Processing"`
- System sets `startedAt` timestamp
- **Manual Action Required:** Admin downloads G-code file from `gcodeUrl` and manually sends it to the physical 3D printer

**Step 4: Completion**
- Admin calls `POST /complete` or `POST /fail`
- Complete: Status → `"Completed"`, sets `finishedAt`
- Fail: Status → `"Failed"`, sets `finishedAt`

**All state transitions are manual** - no automated workers process printing jobs.

## Error Handling

### Common Errors

**Validation Errors (400)**
- Missing required fields
- Invalid field formats
- Invalid status transitions
- Mutual exclusivity violations (productId vs targetOrderItemId)

**Authentication Errors (401)**
- Missing or invalid authentication token
- Expired session

**Authorization Errors (403)**
- User lacks required role
- Operator trying to access admin-only endpoints

**Not Found Errors (404)**
- PrintingJob with specified ID doesn't exist

**State Transition Errors (400)**
- Attempting invalid status transitions
- Example: Starting a job that's not in "Queued" status
- Example: Completing a job that's not in "Processing" status
- Example: Rejected jobs cannot transition further

---

## State Machine Validation

The PrintingService enforces strict state machine rules:

**Valid Transitions:**
- `Pending Review` → `Approved` or `Rejected`
- `Approved` → `Queued` (automatic)
- `Queued` → `Processing`
- `Processing` → `Completed` or `Failed`

**Terminal States:**
- `Rejected` - No further transitions allowed
- `Completed` - Job successfully finished
- `Failed` - Job failed during processing

---

## Job Number Uniqueness

- Job numbers are unique **within** the PrintingJob collection
- The same job number can exist in both SlicingJob and PrintingJob collections
- Example: `"JOB-001"` can exist as both a SlicingJob and a PrintingJob

## Example Usage

### Complete Workflow Example

```bash
# Step 1: User creates printing job from completed slicing job
POST /api/v1/printing/execute
Content-Type: application/json
Authorization: Bearer <token>

{
  "slicingJobId": "64f1a2b3c4d5e6f7a8b9c0d2"
}

# Response: PrintingJob created with status "Pending Review"
# MongoDB auto-generates the job ID (_id)
# gcodeUrl and fileName are copied from the slicing job

# Step 1.5: User checks status of their printing job
GET /api/v1/printing/status/64f1a2b3c4d5e6f7a8b9c0d1
Authorization: Bearer <token>

# Response: Current status (e.g., "Pending Review", "Queued", "Processing", etc.)

# Step 2: Review and approve
POST /api/v1/admin/printing/review
Content-Type: application/json
Authorization: Bearer <admin-token>

{
  "jobId": "64f1a2b3c4d5e6f7a8b9c0d1",
  "action": "approve"
}

# Response: Status changed to "Queued"

# Step 3: Get queued jobs
GET /api/v1/admin/printing/queued
Authorization: Bearer <admin-token>

# Response: List of jobs ready for printing

# Step 4: Start printing
POST /api/v1/admin/printing/start
Content-Type: application/json
Authorization: Bearer <admin-token>

{
  "jobId": "64f1a2b3c4d5e6f7a8b9c0d1",
  "machineId": "PRINTER-01"
}

# Response: Status changed to "Processing", startedAt set, gcodeUrl provided
# Manual Action: Download G-code from gcodeUrl and send to physical printer

# Step 5: Complete printing
POST /api/v1/admin/printing/complete
Content-Type: application/json
Authorization: Bearer <admin-token>

{
  "jobId": "64f1a2b3c4d5e6f7a8b9c0d1"
}

# Response: Status changed to "Completed", finishedAt set
```
